# MiniDSH 开发流程规范

> 状态：Reviewed（2026-10-16 所有者确认，作为流程基线；此前 PROGRESS.md 已按 Reviewed 引用，本次统一文件头状态）
> 适用范围：MiniDSH 全部开发工作。流程变更需先修改本文档并重新 review。

## 1. 总则

1. **文档先行**：任何代码动手之前，对应的设计文档必须已敲定（状态 Review 通过 → Baseline）。
2. **骨架先行，逐模块推进**：先设计并实现骨架（插件内核 + 全部模块间契约），之后每个模块独立走一轮完整循环，一次只推进一个模块。
3. **review 门禁**：设计和代码各设一道 review，均由项目所有者执行。review 通过并明确同意后，才允许执行 git commit。
4. **预算纪律**：每个模块有 LOC 预算。实现完成时统计实际行数，超预算须回砍或说明理由并获批准，不允许默默超支。
5. **能用中文一律用中文**：所有文档（架构、设计、README）与代码注释用中文书写；无法用中文的保持英文——代码标识符、命令、文件路径、协议与 API 字段名、commit message（见 §5）。
6. **注释按大厂标准写详细**：公共导出必有 JSDoc（说明用途、参数、返回值、副作用与错误行为），复杂算法和非显然逻辑必须有行内注释；注释是交付物的一部分，review 时一并检查。

## 2. 文档体系

| 文档 | 位置 | 职责 |
|---|---|---|
| 会话入口 | `AGENT.md` | 流程索引 + 会话交接协议。**每个模块一个新对话，新对话必读** |
| 进度跟踪 | `docs/PROGRESS.md` | 跨会话进度唯一事实源：模块步骤、LOC 实绩、阻塞、下一步动作。交接必更新 |
| 骨架设计 | `docs/architecture.md` | 总体架构、模块分解、跨模块契约、预算总表。**基线文档，改动需重新 review** |
| 开发流程 | `docs/process.md`（本文档） | 流程规范、模板、门禁 |
| 模块设计 | `docs/design/<序号>-<模块名>.md` | 单个模块的详细设计，实现前编写，实现后归档为该模块的权威说明 |
| 模块README | 各模块实现后视需要补充 | 使用说明（可选，不强制） |

模块设计文档编号即实现顺序：`01-config`、`02-llm`、`03-session`、`04-prompt`、`05-tools`、`06-agent`、`07-cli`、`08-plugin-memory`、`09-plugin-mcp`。

文档状态字段三档：`Draft`（起草）→ `Reviewed`（review 通过，可动工）→ `Baseline`（实现完成且验收通过，归档）。

## 3. 单模块开发循环

完整流程七步，每个模块严格执行，禁止跳步：

```text
① 需求        →  ② 设计文档  →  ③ 一个 package  →  ④ 单元测试
                                                        ↓
                                             ⑤ 集成测试  →  ⑥ Review  →  ⑦ Git commit
```

| 步骤 | 内容与门禁 |
|---|---|
| ① 需求 | 澄清目标与范围（对应骨架哪条契约、模块粒度、边界）。需求有歧义不许进 ② |
| ② 设计文档 | 写 `docs/design/NN-module.md`（Draft）→ 所有者 review → 敲定（Reviewed）。骨架阶段（M0）同样走全流程，只是"模块"换成骨架整体 |
| ③ 一个 package | 实现落在**一个** package：`src/<module>/`（01–07）或 `plugins/<name>/`（08–09）。一次只推进一个模块，不跨模块散改；`typecheck` 通过，公共导出有中文 JSDoc |
| ④ 单元测试 | `*.test.ts` 与源码同目录，vitest；覆盖设计文档 §6 的单测点；`pnpm test` 通过 |
| ⑤ 集成测试 | `tests/integration/*.test.ts`：跨模块真实链路（可含临时文件、伪 adapter），验证模块经组合根挂载后的实际行为，不 mock 内部实现；通过后方可进 ⑥ |
| ⑥ Review | 所有者 review 代码，逐条对照设计文档 §7 DoD；LOC 偏差须已说明 |
| ⑦ Git commit | 一次提交对应一个模块的完整产物（文档 + 实现 + 单测 + 集成测试）或一次纯文档/纯修复；按 §5 规范，用户确认后执行 |

单元测试与集成测试是**两道独立门禁**：前者验证模块内部语义，后者验证模块在骨架中的挂载与协作，二者缺一不可，不互相替代。

## 5. 提交规范

- commit message：conventional commits，英文小写 scope，例：`feat(agent): turn/step loop with parallel tool scheduling`、`docs(design): llm module design`、`test(tools): permission waterfall`。
- 一个 commit 对应一个模块的完整循环产物（文档 + 实现 + 测试），或一次纯文档/纯修复提交。
- 提交前必须展示变更摘要（文件列表 + 增删行数），确认后才执行。
- 不使用 `--no-verify`；不 amend 已 review 的提交，改走新提交。

## 6. 预算纪律

- 统计口径：模块全部 `.ts` 源码，排除 `*.test.ts` 与 `tests/` 目录；01-07 位于 `src/<module>/`，08/09 位于 `plugins/<name>/`。
- 统计命令（Git Bash）：`git ls-files 'src/<module>/**/*.ts' 'src/<module>/*.ts' 'plugins/<name>/**/*.ts' 'plugins/<name>/*.ts' | grep -v '\.test\.ts$' | xargs wc -l`。
- **口径陷阱（M0 实测）**：git pathspec 的 `**` 只匹配**子目录**下的文件，不会匹配 `src/<module>/*.ts` 这一层——只写 `'src/<module>/**/*.ts'` 会静默漏计模块顶层文件（M0 漏了 contracts.ts / errors.ts / index.ts 共 539 行）。因此每个模块都要**同时**给出 `**` 与单层两个 pattern。
- 偏差超过预算 ±20% 时，在模块文档"验收标准"下追加一行说明原因。
- 产品代码总预算：逐模块预算合计 ~11.5k（architecture.md §4，为实际预期值），总体目标 ~10,000 行（允许浮动），**硬上限 20,000 行**，任何情况下不得突破；测试代码不计入。

## 7. 会话交接与进度跟踪

一个模块一个新对话，**新对话不继承任何历史上下文**，因此一切交接信息必须落盘：

1. **开场（接手方）**：读 `AGENT.md` → 读 `docs/PROGRESS.md` → 读当前模块设计文档 → 确认状态为 Reviewed 才动工。
2. **收尾（交接方）**：更新 `docs/PROGRESS.md`（步骤打勾、LOC 实绩、新发现问题写进"遗留与阻塞"、顶部"下一步动作"写下个会话要做的第一件事）。
3. **偏离回写**：实现偏离设计文档时，必须回写设计文档的"验收标准"小节，不能只留在对话中。
4. **不自动提交**：用户未明确要求不得 `git add`/`commit`/`push`；改动留在工作区，由用户在 ⑦ 确认后提交。
5. **进度文件是唯一事实源**：`docs/PROGRESS.md` 与对话内容冲突时，以 PROGRESS.md 为准。

## 8. Definition of Done（模块级）

- [ ] 设计文档状态为 Reviewed 且实现未偏离文档（偏离处已在文档中补充并说明）
- [ ] `pnpm typecheck`、`pnpm lint`、`pnpm test` 全部通过
- [ ] §6 列出的单元测试点全部覆盖并通过
- [ ] §6 列出的集成测试点全部覆盖并通过
- [ ] LOC 在预算内（或偏差已说明）
- [ ] 所有者已 review 代码
- [ ] 设计文档状态更新为 Baseline
- [ ] `docs/PROGRESS.md` 已更新（步骤、LOC 实绩、下一步动作）
- [ ] 已按第 5 节规范提交
